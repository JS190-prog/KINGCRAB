# 시맨틱 온톨로지에서 키네틱 군체로

## OpenCrab 에이전트 CLI, KINGCRAB의 설계

온톨로지는 지식을 설명하는 구조다. 어떤 개념이 있고, 서로 어떤 관계를 맺고 있으며, 무엇을 근거로 삼는지 정리한다. 이 단계에서 온톨로지는 대체로 정적이다. 잘 만들어진 지식 지도이지만, 지도 자체가 목적지를 향해 걷지는 않는다.

KINGCRAB은 `opencrab.sh`가 만든 세계관을 CLI 안으로 확장하려는 시도다. OpenCrab의 팩, 프로젝트, 워크플로, MCP, 그래프는 지식을 저장하고 연결하는 기반이다. KINGCRAB은 그 기반 위에 TUI 컨셉의 CLI 에이전트 패널을 얹어, 사용자가 자신의 온톨로지 세계를 직접 선택하고 지시하고 실행 결과까지 확인할 수 있게 한다.

즉, KINGCRAB은 OpenCrab과 분리된 또 하나의 지식 서비스가 아니다.

> `opencrab.sh`의 시맨틱 세계를 터미널 안에서 움직이는 키네틱 에이전트 도구로 확장하는 클라이언트이자 실행 계층이다.

사용자는 TUI에서 프로젝트를 고르고, 해당 프로젝트의 팩을 QUEEN의 작업 맥락으로 선택한다. 상단에서는 모델·MCP·CLI·워커 상태를 확인하고, 중앙 대화창에서는 KING에게 미션을 지시한다. 좌우 패널은 군체의 상태, 선택된 온톨로지, 실제 연결된 자산과 작업 결과를 보여준다. CLI이지만 단순한 명령어 모음이 아니라, OpenCrab 세계관을 탐색하고 작동시키는 조종석에 가깝다.

KINGCRAB은 이 지도를 움직이게 하려는 시도다.

핵심은 단순하다.

> 온톨로지를 저장하는 데서 끝내지 않고, 온톨로지와 에이전트를 연결해 실제 일을 수행하게 만든다.

이를 위해 KINGCRAB은 온톨로지를 시맨틱 영역에서 키네틱 영역으로 옮긴다. 시맨틱이 “무엇이 무엇과 어떤 의미로 연결되는가”를 다룬다면, 키네틱은 “그 연결을 사용해 다음에 무엇을 할 것인가”를 다룬다.

```text
시맨틱 온톨로지
개념 · 관계 · 근거 · 규칙
          ↓
키네틱 실행
미션 · 역할 · 도구 · 승인 · 결과
```

이 전환이 일어나면 온톨로지는 참고자료가 아니라 작업의 재료가 된다.

## 챗봇이 아니라 작업하는 구조

일반적인 챗봇은 질문을 받고 답을 생성한다. 멀티에이전트 시스템은 여러 모델에게 질문을 나누어 맡길 수 있다. 그러나 모델을 여러 개 붙였다고 해서 업무체계가 생기는 것은 아니다.

KINGCRAB이 만들려는 것은 모델의 숫자가 아니다. 미션이 정의되고, 지식이 선택되고, 작업이 분배되고, 결과가 검증되는 실행 구조다.

사용자가 “이 자료를 바탕으로 새로운 브랜드 전략을 만들어줘”라고 말하면 KINGCRAB은 한 번에 긴 답변을 뱉는 대신 다음 질문을 먼저 구조화한다.

1. 이 작업의 최종 목적은 무엇인가.
2. 목적을 달성하려면 어떤 지식이 필요한가.
3. 어떤 온톨로지 팩과 근거를 사용할 것인가.
4. 어떤 작업을 어떤 순서로 수행할 것인가.
5. 결과를 무엇으로 검증할 것인가.

여기서 미션은 단순한 프롬프트가 아니다. 실행 가능한 작업 계약이다. 목표, 범위, 허용된 자산, 출력 형식, 검증 조건이 함께 있어야 한다.

## 군체형 업무체계

KINGCRAB의 군체는 생물학적 군체를 흉내 내기 위한 장식이 아니다. 복잡한 업무를 역할별로 분리하고, 각 역할이 자신의 판단 범위 안에서 움직이게 하기 위한 운영 모델이다.

### KING: 미션을 정의하는 존재

KING은 가장 높은 수준의 추론을 맡는다.

KING의 역할은 직접 모든 일을 하는 것이 아니다. 무엇을 해결해야 하는지 정의하고, 문제를 작업 단위로 나누고, 순서와 의존성을 설계한다.

```text
목표 정의
   ↓
작업 그래프 설계
   ↓
파이프라인 구성
   ↓
역할과 자원 배정
```

예를 들어 브랜드 전략을 만든다면 KING은 시장 조사, 고객 정의, 경쟁 분석, 브랜드 포지셔닝, 실행안, 검증이라는 작업 그래프를 만든다. 각 단계가 끝나야 다음 단계로 갈 수 있는지, 병렬로 진행할 수 있는지를 결정한다.

KING이 약하면 워커가 아무리 많아도 각자 다른 방향으로 달린다. 따라서 KING은 가장 강한 추론과 가장 넓은 시야를 가져야 한다.

### QUEEN: 온톨로지를 모으고 정리하는 존재

QUEEN은 지식의 관리자다.

온톨로지 팩을 검색하고, 프로젝트에 연결된 팩을 확인하고, 미션에 필요한 지식을 골라 작업의 맥락으로 공급한다. 필요하면 새로운 온톨로지의 구조를 계획하고, 기존 팩의 중복·충돌·공백도 살핀다.

QUEEN이 중요한 이유는 모든 지식을 모든 작업에 넣지 않기 때문이다. 필요한 순간에 필요한 팩만 선택해야 한다. 온톨로지 팩이 수백 개, 수천 개로 늘어날수록 전체를 한 번에 모델에게 넣는 방식은 비효율적이다.

좋은 QUEEN은 다음을 구분한다.

| 구분 | QUEEN의 판단 |
| --- | --- |
| 관련성 | 이 미션에 실제로 필요한 팩인가 |
| 근거성 | 주장과 원문 근거가 연결되어 있는가 |
| 최신성 | 지금도 유효한 정보인가 |
| 충돌 | 다른 팩과 상반된 주장이 있는가 |
| 권한 | 이 세션이 사용할 수 있는 팩인가 |

따라서 QUEEN은 단순 검색기가 아니다. 지식의 선택과 배치를 담당하는 온톨로지 오케스트레이터다.

### WORKER: 여러 온톨로지를 품고 실행하는 존재

WORKER는 실제 작업을 수행한다. 코드를 작성하고, 문서를 분석하고, 자료를 비교하고, 정해진 형식의 산출물을 만든다.

여러 WORKER가 동시에 움직일 수 있지만, 아무 일이나 마음대로 시키지 않는다. KING이 정의한 작업 슬롯과 QUEEN이 공급한 온톨로지 맥락 안에서 제한된 일을 수행한다.

```text
미션: 브랜드 전략 작성

WORKER 1  시장 자료 비교
WORKER 2  경쟁 브랜드 구조 분석
WORKER 3  고객 문제와 가치 제안 정리
WORKER 4  초안의 근거 연결 점검
```

여기서 온톨로지는 워커의 수가 아니다. 300개의 팩이 있다고 300명의 워커를 만들 필요는 없다. 온톨로지는 공유되는 지식 맥락이고, 워커는 실제로 실행할 작업 슬롯에만 배정된다.

이 구분이 있어야 토큰과 실행 비용이 폭발하지 않는다.

### SOLDIER: 약한 구조와 낭비를 제거하는 존재

SOLDIER는 공격적인 실행자가 아니라 방어선이다.

약한 온톨로지, 근거가 없는 주장, 중복된 관계, 의미 없는 작업 루프를 찾아낸다. 품질이 낮은 결과를 바로 전체 그래프에 편입하지 않고 격리하거나 보류한다. 워커가 같은 일을 반복하거나 이미 실패한 경로를 다시 밟으면 작업을 종료하거나 KING에게 되돌린다.

권한 관리도 SOLDIER의 역할이다. 리벡, 즉 RBAC(Role-Based Access Control)를 통해 어떤 역할이 어떤 팩·프로젝트·도구에 접근할 수 있는지 통제한다.

```text
KING      미션 설계 권한
QUEEN     온톨로지 조회·구성 권한
WORKER    할당된 작업·도구 권한
SOLDIER   검증·차단·권한 점검 권한
ORACLE    검증된 결과 확정 권한
```

중요한 것은 SOLDIER가 지식을 무조건 삭제하지 않는다는 점이다. “약하다”는 판정을 내렸다면 그 이유와 근거를 남기고, 격리·보류·폐기 중 어떤 조치를 했는지 기록해야 한다. 지식 시스템에서 삭제는 마지막 조치여야 한다.

### ORACLE: 결론을 확정하는 존재

ORACLE은 결과를 멋지게 포장하는 마지막 생성기가 아니다. 결과가 미션의 조건을 충족했는지, 근거가 연결되어 있는지, 산출물이 실제로 존재하는지를 검사하는 QA 역할이다.

ORACLE은 두 가지 결정을 내린다.

```text
검증 통과 → 결론 확정
검증 실패 → 부족한 단계로 되돌림
```

예를 들어 답변은 그럴듯하지만 출처가 없을 수 있다. 코드가 생성됐지만 테스트가 실행되지 않았을 수도 있다. 계획은 완성됐지만 실제 파일이 저장되지 않았을 수도 있다. 이런 결과는 성공처럼 보이지만 ORACLE의 기준에서는 미완료다.

ORACLE이 부족한 결과를 다시 루프로 돌려보내면 시스템은 단순히 답을 반복하는 것이 아니라 실패 원인을 반영해 다음 실행을 설계할 수 있다.

## 실제 실행 흐름

KINGCRAB의 한 작업은 다음과 같이 흐른다.

```text
사용자 요청
    ↓
KING 미션 정의
    ↓
QUEEN 온톨로지 선택·정리
    ↓
SOLDIER 권한·품질·중복 점검
    ↓
WORKER 작업 실행
    ↓
SOLDIER 결과 방어·낭비 루프 차단
    ↓
ORACLE QA
    ├─ 통과: 결론과 산출물 반환
    └─ 실패: 필요한 단계로 재진입
```

이 구조의 핵심은 역할이 순서대로 한 번씩 호출되는 것이 아니다. 상황에 따라 QUEEN이 다시 지식을 보강할 수 있고, SOLDIER가 특정 워커를 멈출 수 있으며, ORACLE이 KING에게 미션 정의를 다시 요청할 수 있다.

즉, 군체는 직선형 파이프라인이 아니라 검증 가능한 루프다.

## opencrab.sh에서 TUI CLI로

OpenCrab의 웹 경험이 팩과 프로젝트를 시각적으로 탐색하는 공간이라면, KINGCRAB은 같은 자산을 작업 중심의 터미널 경험으로 가져온다.

```text
opencrab.sh
팩 · 프로젝트 · 그래프 · 워크플로 · MCP
                    ↓ 연결
KINGCRAB TUI CLI
KING · QUEEN · WORKER · SOLDIER · ORACLE
                    ↓ 실행
미션 · 코드 · 문서 · 분석 · QA 결과
```

이 확장은 두 가지를 함께 보존해야 한다. 첫째, OpenCrab에서 만들어진 온톨로지 팩과 프로젝트의 정체성이다. 둘째, CLI 에이전트가 실제 작업을 수행하는 실행 상태다. 그래서 KINGCRAB은 로컬 런타임과 OpenCrab MCP를 연결하고, 사용자의 선택 범위와 권한을 세션에 저장한다. 패널을 닫아도 미션 상태가 사라지지 않고, 다시 열면 같은 프로젝트와 대화, 온톨로지 맥락을 이어갈 수 있어야 한다.

TUI는 장식이 아니다. 상태를 보여주는 운영 인터페이스다.

- 왼쪽은 KING의 미션과 프로젝트·세션 구조를 보여준다.
- 중앙은 사용자와 에이전트의 대화, 작업 진행, 산출물을 보여준다.
- 오른쪽은 QUEEN이 선택한 OpenCrab 온톨로지와 워커 자산을 보여준다.
- 상단은 현재 모델, MCP, CLI, 워커 상한과 실제 연결 상태를 보여준다.

이렇게 하면 OpenCrab의 세계관이 “팩을 만들어 보관하는 곳”에서 “팩을 선택해 일을 시키는 곳”으로 확장된다.

## 시맨틱에서 키네틱으로의 변화

시맨틱 온톨로지는 다음을 잘한다.

- 개념을 구분한다.
- 관계를 표현한다.
- 근거를 연결한다.
- 지식의 구조를 재사용한다.

키네틱 온톨로지는 여기에 다음을 추가한다.

- 어떤 조건에서 행동할지 정의한다.
- 어떤 역할이 실행할지 결정한다.
- 어떤 도구를 사용할지 제한한다.
- 결과를 어떤 기준으로 평가할지 기록한다.
- 실패하면 어느 단계로 되돌아갈지 정한다.

그래서 KINGCRAB에서 온톨로지는 “브랜드란 무엇인가”에서 멈추지 않는다.

```text
브랜드 개념
   ↓
브랜드를 평가하는 기준
   ↓
필요한 근거 팩
   ↓
분석 작업
   ↓
전략 산출물
   ↓
QA와 다음 행동
```

개념이 행동으로 이어질 때 온톨로지는 업무 시스템이 된다.

## 기존 멀티에이전트와 무엇이 다른가

에이전트를 여러 개 띄우는 것만으로는 군체가 되지 않는다. 군체가 되려면 최소한 네 가지가 필요하다.

1. 역할별 책임 경계가 있어야 한다.
2. 공유하는 지식의 구조가 있어야 한다.
3. 작업을 배정하고 종료하는 계약이 있어야 한다.
4. 결과를 검증하고 되돌리는 루프가 있어야 한다.

KINGCRAB은 모델을 무작정 늘리는 대신, 미션·온톨로지·작업 슬롯·권한·증거·QA를 연결한다. 따라서 성능은 에이전트 수의 단순한 합이 아니라 다음 조합에서 나온다.

```text
시스템 성능
= 미션의 명확성
× 온톨로지의 적합성
× 작업 분배의 정확성
× 검증의 엄격성
```

어느 한 항목이 0이면 전체 결과도 흔들린다.

## 한계와 운영 원칙

KINGCRAB은 AGI를 선언하는 장치가 아니다. 온톨로지가 많아진다고 자동으로 지능이 생기는 것도 아니다. 잘못된 팩이 많으면 오히려 잘못된 경로가 더 촘촘해질 수 있다.

그래서 다음 원칙이 필요하다.

- 생성된 결과를 원본 근거와 같은 수준의 사실로 취급하지 않는다.
- 모든 중요한 주장과 관계에 Evidence를 연결한다.
- 약한 온톨로지는 삭제 전에 격리하고 판정 이유를 남긴다.
- 워커 수와 온톨로지 수를 같은 것으로 계산하지 않는다.
- 권한 없는 팩과 도구를 작업 맥락에 섞지 않는다.
- ORACLE이 확인하지 않은 결과를 완료라고 부르지 않는다.

KINGCRAB의 목표는 인간을 대신해 모든 것을 결정하는 것이 아니다. 사람이 가진 지식과 도구, 그리고 여러 모델의 능력을 하나의 실행 가능한 업무 구조로 묶는 것이다.

## 결론: 지식이 움직이기 시작할 때

온톨로지는 지식을 구조화한다. 에이전트는 그 지식을 사용해 행동한다. 군체형 업무체계는 그 행동을 역할과 책임으로 나눈다. QA 루프는 결과를 다시 지식과 실행의 개선으로 돌려보낸다.

KINGCRAB은 `opencrab.sh`의 팩과 프로젝트 세계, MCP 연결, 그래프 지식을 하나의 TUI 컨셉 CLI 안에 연결하려 한다.

```text
온톨로지
    ↓
미션
    ↓
군체 실행
    ↓
검증
    ↓
더 나은 온톨로지와 다음 미션
```

시맨틱 온톨로지가 세계를 이해하기 위한 지도라면, 키네틱 온톨로지는 그 지도 위에서 실제로 움직이는 업무체계다.

KINGCRAB이 만들려는 것은 더 많은 답변이 아니다.

> 지식이 역할을 얻고, 역할이 행동을 얻고, 행동이 검증 가능한 결과로 남는 구조다.

그리고 그 구조는 웹과 터미널 중 하나를 선택하는 문제가 아니다. `opencrab.sh`가 지식의 세계를 열었다면, KINGCRAB은 그 세계 안에서 사용자가 직접 미션을 만들고 군체를 움직이며 결과를 확인하는 확장된 작업 공간이다.
